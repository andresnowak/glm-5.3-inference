Bottom line. Both 16-GPU low-latency deployments served GLM-5.3 end to end over CXI. The measured GH200/CUDA stack is substantially faster: 4.5–6.0× more output throughput across the concurrency sweep and about 6× more decode throughput. This is a comparison of validated deployments, not isolated hardware: CUDA used FP8 KV, BATCHED_DEEPGEMM, and graphs; ROCm used BF16 KV, Triton FP8 MoE, and eager execution because UCCL graph capture faulted.

1. Test configuration and validation

Hardware and topology

  • Clariden: 4 nodes × 4 GH200, 95.0 GiB GPU memory each
  • tensor_parallel_size=2, data_parallel_size=8
  • Expert parallel enabled: EP=16, 16 of 256 experts per GPU
  • UCCL e22a3e8f, built with libfabric/CXI
  • FP8 KV cache and NUMA binding

End-to-end proof

CUDA job 3411463 completed in 6:44. It served POST /v1/chat/completions with HTTP 200 and a coherent 337-token answer using deepep_low_latency, EP=16.

Four nodes are the measured floor: at EP=8, routed-expert weights require about 105 GiB/GPU and do not fit.

7. What HT required

Scope matters: docs/deepep-high-throughput.md records HT hangs under the 256k and earlier configurations. The raw TSVs separately contain successful-looking HT benchmark datapoints with deep_gemm, lower context, and memory utilization 0.80, but the repository has no retained run IDs or raw logs tying them to a final reliable configuration. Preserve the values as historical recorded measurements; treat current HT serving as unusable until the dedicated hang is fixed and the benchmark is reproduced.
  1. Use upstream UCCL. The stale swiss-ai fork crashed in the internode kernel; all retained measurements use upstream e22a3e8f.
  2. Force --moe-backend deep_gemm. FlashInfer CUTLASS autotuning performs collective all-reduces over rank-dependent local shapes under EP, causing mismatched collectives and deadlock.
  3. Set GPU_MEM_UTIL=0.80. HT’s ragged activation layout OOMs at 0.90.
  4. Keep the CUDA-graph guard fix. vLLM’s HT guard is behind the wrong early return. Disabling graphs alone did not solve the original hang, but the guard is still a real correctness fix.

In the unresolved HT-hang investigation, disproved causes included shared-memory size, architecture, rank count, buffer capacity, FP8 dispatch, zero-token ranks, NUMA binding, graph capture by itself, and changing QPs per rank from 10 to 24. Standalone UCCL dispatch/combine passed; the remaining hang was specific to the vLLM integration/configuration.

The estimate includes 0.15 s for transferring about 3.3 GB of MLA KV at measured UCCL Slingshot bandwidth. This deployment was not wired or run end to end. NIXL 1.3.0 is present in the CUDA image, but connector work remains.

11. CUDA conclusions

  • General serving: use deepep_low_latency.
  • Long prefill tier: historical HT datapoints are compelling from 4k onward, but must be reproduced after the unresolved vLLM startup hang is fixed.
  • Short-context decode: AGRS can be fastest, but loses too much KV capacity for long context.
  • Best measured operating point: LL at concurrency 16 balances throughput and latency.
  • Do not present projections as measurements: P/D disaggregation, 8-node EP=32, native 1M context, and MTP remain unvalidated.

12. ROCm / MI300A validation

Validated deployment

  • 4 nodes × 4 AMD MI300A, 128 GiB unified HBM per APU
  • TP=2, DP=8, EP=16
  • UCCL d94b5bf2 with the runtime-top-k assertion fix
  • UCCL low latency over libfabric/CXI
  • AITER sparse MLA; Triton FP8 MoE; native vLLM sampler
  • BF16 KV cache; GPU_MEM_UTIL=0.70

Evidence

Smoke job 640358 returned an HTTP 200 completion with 256 generated tokens. Benchmark job 640649 reached API readiness and completed all 11 repository suite points with every request successful.

Memory: 61.59 GiB weights/non-Torch, 1.73 GiB peak activation, 26.28 GiB KV cache, and 304,656 KV tokens per engine.

Why eager mode? ROCm graph job 640433 faulted during capture in UCCL kernel intranode::barrier<4> with HSA_STATUS_ERROR_EXCEPTION. The final benchmark therefore used --enforce-eager. Jobs at memory utilization 0.85 and 0.80 hit host OOM during warm-up or concurrency 16; 0.70 completed the full suite.

What the comparison supports

  • Measured: the tested CUDA deployment delivers 4.5–6.0× more output throughput in concurrency scaling and 5.7–6.1× more in decode.
  • Measured: ROCm scales from 3.27 to 93.20 output tok/s between concurrency 1 and 64, a 28.5× increase.
  • Measured exception: ROCm’s 1k prefill TTFT was 0.80 s versus CUDA’s 0.83 s, but CUDA retained 3.76× higher output throughput for that point.
  • Not established: how much of the gap comes from hardware versus graph mode, KV dtype, vLLM revision, or MoE kernel choice.

14. Combined conclusions

  • Both platforms completed end-to-end GLM-5.3 low-latency serving over UCCL/CXI at TP=2, DP=8, EP=16.
  • The current GH200/CUDA deployment is the production performance choice.
  • The MI300A/ROCm deployment is functional, reproducible, and stable at memory utilization 0.70, but needs graph-safe UCCL and a faster MoE path before performance is competitive.
  • ROCm HT serving, graph execution, FP8 KV, and a DeepGEMM-class MoE backend remain unvalidated.
